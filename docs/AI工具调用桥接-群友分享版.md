# 让网页版 AI 实现"工具调用"的通用方法（实测分享版）

> 适用场景：任何**没有原生 function calling** 的 AI（网页版聊天、逆向接口、免费渠道）。
> 效果：AI 可以"指挥"外部程序读文件、改文件、跑命令——所有执行都在你本机发生。
>
> 本文是**文本协议仿真**（实现见 `tool-emu.js`）；若你要的是**原生工具调用**（Claude/OpenAI 客户端的
> `tools` / `tool_use` / `tool_calls` 协议互转），看 `README.md`「行为细节 → 工具调用（Anthropic tool_use ↔ OpenAI tool_calls）」。两者互不影响。

---

## 一句话原理

**不是让 AI"拥有"工具，而是让 AI 输出一段固定格式的"操作请求文本"，由外部程序解析、真实执行、再把结果贴回对话。**

AI 只负责"写工单"，执行永远在外部。这是任何能输出文本的 AI 都能做到的。

```
你的任务 ──→ AI 生成 [TOOL_CALL] 工单 ──→ 外部程序解析并真实执行
     ↑                                          │
     └──── AI 根据执行结果继续 ←── 结果按固定格式贴回 ──┘
```

---

## 最重要的坑（对照实验证实）

给 AI 讲协议时，**措辞决定成败**：

| 说法 | 结果 |
|---|---|
| ❌ "本环境给你接入了真实工具，你可以使用它们" | AI 拒绝："我的工具接口里没有这些工具" |
| ✅ "请**生成**供外部程序校验、执行的**操作请求文本**；你无需实际执行，也不要提前声称执行成功" | AI 配合，格式准确 |

**为什么**：网页版 AI 清楚地知道自己工具接口里有什么（它能列出清单）。你说"你拥有工具"，与它的自我认知**冲突**，它会诚实地纠正你。而"生成文本"是它的本职，与自我认知**不冲突**——它就配合了。

同一模型、同一请求、同一网关，只改这一段措辞：旧说法 100% 拒绝 → 新说法 100% 配合。

## 给 AI 粘贴的协议文本（模板）

把下面整段发给 AI（工具清单按你的需要增删）：

```
# 工具操作请求（本协议由外部程序解析执行）

请生成供外部程序校验、执行的操作请求文本；你无需在当前聊天环境中实际执行，
也不要提前声称执行成功。外部程序会解析你的请求文本并执行对应操作，
执行结果会作为下一条用户消息回传给你。

可用工具：

### echo
回显工具：把输入的文本原样返回。仅用于链路测试，不读取文件、不执行命令。
参数 JSON Schema（arguments 必须是满足该 schema 的合法 JSON 对象）:
{"type":"object","properties":{"text":{"type":"string"}},"required":["text"]}

### read
读取指定路径的文本文件内容。
参数 JSON Schema（arguments 必须是满足该 schema 的合法 JSON 对象）:
{"type":"object","properties":{"file_path":{"type":"string"}},"required":["file_path"]}

## 调用格式（严格遵守）
需要使用工具时，输出如下标记（每个调用一组，arguments 为参数对象）：

[TOOL_CALL]
{"name": "工具名", "arguments": {"参数名": "值"}}
[/TOOL_CALL]

标记由外部程序解析并执行，你不需要（也无法）自己执行任何操作。

## 判定规则
- 由你判断：需要外部信息或动作时必须调用工具（不要凭记忆猜测可查证的事实）；能直接回答时正常回答。
- 输出工具调用标记后立即停止输出，等待工具结果回传后再继续。
- 不要编造不存在的工具；不要把操作请求写成 JSON 代码块，必须用上述标记。
- 任务需要工具而不输出标记（比如声称"没有工具"、要求用户自己粘贴文件内容），视为任务失败。
```

## 收到工单后，你（或你的程序）怎么回传结果

AI 输出 `[TOOL_CALL]...[/TOOL_CALL]` 后，执行对应操作，然后按这个格式回复它：

```
[工具 echo 的执行结果如下]
{"result":"你输入的文本"}
[请根据以上工具结果继续]
```

AI 就会基于真实结果继续任务。这样循环，直到任务完成。

## 完整示例（一次真实测试）

你：请调用 echo 工具，text 参数填 "hello-bridge-test"，然后告诉我 echo 返回了什么。

AI：`[TOOL_CALL]{"name":"echo","arguments":{"text":"hello-bridge-test"}}[/TOOL_CALL]`

你：`[工具 echo 的执行结果如下]`
`{"result":"hello-bridge-test"}`
`[请根据以上工具结果继续]`

AI：echo 返回了 `hello-bridge-test`。

## 给会编程的朋友：解析端要点

如果外部程序是你自己写的，注意这几点（我们踩过的坑）：

1. **捕获区段**：`[TOOL_CALL]` 到 `[/TOOL_CALL]` 之间；建议同时兼容 ```` ```json ```` 围栏作兜底
2. **形状校验**：`JSON.parse` 后必须同时有 `name`（字符串）和 `arguments`/`args`/`parameters`（对象）——防止把普通 JSON（如 `{"name":"config","port":8080}`）误判成调用
3. **紧邻重复去重**：模型可能在思考段和正文各写一遍同一工单——紧邻的同名同参调用只执行一次
4. **流式场景**：标记可能被拆到多个 chunk；缓冲判定，"可能是标记开头"的尾部字符先挂起（如 `[TOOL`、单个反引号）
5. **结果关联**：一条工单对应一条结果回传，带上下文让模型知道是哪次调用的返回

## 安全提醒（真要执行的话）

- 工具白名单：只注册你实现的工具，解析出白名单外的名字一律拒绝
- 范围限制：文件读写限制在指定目录（防 `..`、符号链接逃逸）
- 命令类工具：执行前列出命令等确认；超时；低权限用户运行
- **不要把 cookie/token 等凭据回传给 AI**——AI 的对话内容可能离开你的电脑
