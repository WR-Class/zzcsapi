# 调度详解

> 本文从 README 拆出（v1.18.8）：README 只留调度顺序摘要（含「有效优先级」公式），本文收全量语义——
> 同渠道重试、熔断冷却分级、加权轮询、自动权重（v1.18.63 起可选生效）、有效优先级、含图请求的候选裁剪。
> 协议与渠道配置见 [docs/protocols.md](protocols.md)；运行期五组开关见 [docs/runtime-settings.md](runtime-settings.md)。

## 调度顺序

1. 按请求的 `model` 在所有 `enabled` 且协议匹配的渠道里查 alias
   · **协议匹配 = 同协议优先，跨协议兜底**：三条客户端路由都能用 `openai` / `anthropic` / `gemini` 三种协议的渠道
     （出站自动转原生格式，见「原生出站」），但**先在同协议的渠道里选**，同协议没有/都失败才用另外两种协议，
     最后才是 notion → notion-agent → workbuddy → genspark → codex 这些文本链兜底。
     你现有的 `openai` 渠道先后顺序因此**完全不受影响**（原生协议渠道只是候选链尾部多出来的一层）。
2. 候选 = 命中的渠道 ∪ 探测结果里识别到该模型的渠道（有效优先级 -0.5）
3. 排序：冷却中 → 末位；`down` → 倒数第二；`probation`（探测半愈合过、欠账还在）→ 排在健康渠道之后；同状态按**有效优先级**降序，再看 latency
4. **加权轮询**：填了 `weight` 的渠道按权重比例决定"谁排第一"（见下）
5. **会话粘性**（`sessionAffinity.enabled`，v1.17，默认关）：带会话标识的请求，若这条会话上次成功落在候选链里的某家、
   且那家还能上场（不在冷却、不是 `down`），就把**它**提到第一位——覆盖上面第 4 步的结果。
   它只改"谁是第一位"，其余候选顺序、冷却判断、兜底链一律不动；命中的请求**不消耗** SWRR 状态
   （所以"落点集中在一家、份额统计仍是 50/50"是设计如此，不是 bug）
6. **含图请求**先按「图片能力门」裁剪候选（见下）；纯文本请求不受影响
7. 依次尝试直到成功；全部失败返回 502 + 错误详情
8. **同渠道重试**（`retries.perChannel`，v1.9.3 起真正接线）：对**同一家**失败后原地再试几次，
   试满才换下一家。只重试"可重试的失败"（5xx / 网络错误 / 超时），4xx 一律不重试——重发同一个
   请求只会再收一次同样的拒绝，其中不少还是客户端自己的参数错。每次尝试**各记一次失败**
   （`consecutiveFail` 与指数退避按真实尝试次数增长），重试成功则照常清零。
   配置里没写这个键时是 `0`（不重试 = 与接线前行为一致）；上限钳到 5，怕写错数字把上游调用量放大十倍。
   **v1.18.45 起多一条否决权**：上游自己在报文里说了 `isRetryable:false` 时，跳过原地重试、直接换下家
   （见下「上游否决」）。

## 同渠道重试（`retries.perChannel`）

| 值 | 含义 |
| --- | --- |
| 缺省 / `0` | 不重试：第一次失败就换下一候选（v1.9.3 以前的唯一行为） |
| `1` | 同一家失败后原地再试 1 次，仍失败才换下家 |
| `n` | 最多再试 n 次（`n` 被钳到 0..5） |

- 只对 5xx / 网络错误 / 超时生效；`401/402/403/404/408/429` 与其它 4xx **直接换下家**（属于渠道侧或
  客户端侧问题，原地重发没有意义）。
- 冷却（`cooldownUntil`）只影响"下一次请求选不选它"，不挡这次原地重试——重试要吃的就是瞬时抖动。
- 每次尝试都记账：`perChannel: 1` 且上游一直 502 时，该渠道一次请求里会累加 2 次失败、更快进入
  `down` 与更长的退避。502 的 `attempts` 里带 `attempt` 字段，事后能看出重试痕迹。
- 已经在向客户端写 chunk 之后的失败**不重试**（半截回复不换渠道，见 [docs/behavior.md](behavior.md)「流式失败」）。

## 重试预算（`retries.budgetAttempts` / `retries.budgetMs`，v1.18.88）

`perChannel` 只管"同一家原地重试几次"，`maxModelFallbacks` 只管"最多换几家"——两者的**乘积**才是
一次客户端请求真正能发出的上游调用数。候选 40 家 × 每家 6 次 = **240 发**，全部发生在**一个**客户端请求里；
体感就是"网关卡住、CPU 没满、日志还在刷"，而人只会去查上游。重试预算就是给这个乘积加一道总闸。

| 配置 | 缺省 | 含义 |
| --- | --- | --- |
| `retries.budgetAttempts` | `32` | 一次请求最多发多少**上游尝试**（同渠道重试也算）。钳到 1..500，`0` = 显式不限 |
| `retries.budgetMs` | `600000`（10 分钟） | 一次请求最多花多久。钳到 1s..1h，`0` = 显式不限 |

三条语义（都能被 `test/route-header-budget-e2e.test.js` 的真值表直接验）：

1. **计数单位是"上游尝试"，不是"换了几家"**——同渠道重试也吃预算。否则 `perChannel` 会把预算按倍数放大，
   这个闸就等于没装。
2. **两条上限互相独立、先到先停**（次数超了停 / 耗时超了也停，互不影响）。命中的是**第一条**先到的，
   且**只记一次**（后面的都是"已经在预算外"的重复，再记只会把两个计数搅在一起）。
3. **命中时如实回 502**，并在 `error.budget` 里给明细（`hit` / `attemptsUsed` / `attemptsMax` / `elapsedMs` / `msMax`），
   文案直接点名 `retries.budgetAttempts` 或 `retries.budgetMs`。**不伪装成"渠道全部失败"**——后者会让人去查上游，
   而真因是他的重试配置在这个请求里已经烧完了。同时**不再往后遍历候选**（否则剩下每家各推一条废话进 `attempts`，
   让"试了几家"看起来比实际多）。

为什么缺省取这么宽：正常请求（1~3 家、`perChannel ≤ 1`）根本够不着，只有"链很长 + 全在抖"的病态场景才会命中。
配 `0` 关掉它 = 老配置行为一字不变。

配套两个可观测点：响应头 `X-ZZCSAPI-Route` 的 `pick=exhausted`（与 `pick=all-failed` 分得开）、
以及 `zzcsapi_retry_budget_exhausted_total{reason="attempts"|"elapsed"}`（见 [docs/runtime-settings.md](runtime-settings.md) ③）。

### 上游否决：`isRetryable:false`（v1.18.45，目前只有 notion）

上游有时会在**报文里**明说"这次不是抖动、重试没用"。判据只认报文里这句话，不看渠道是谁：

```
{"type":"error","message":"Something went wrong. Please try again later.","traceId":"…",
 "id":"…","isRetryable":false,"subType":"temporarily-unavailable"}
```

命中时**跳过原地重试**（`perChannel` 配了也不试），直接换下一候选。两个理由，第二个才是重点：

1. 那一发是白等的（几百毫秒到几秒），上游已经说了没用。
2. **对一家正在拒绝我们的账号多敲一次门，只会把它往墙里推得更深。** notion 的软墙是账号级拒绝，
   它的成因里有一条尚未验证的怀疑：高频用 Node 客户端敲门会把账号推进「账号状态」那个维度
   （见 [docs/notion-attachment-upload-research.md](notion-attachment-upload-research.md) §7）——
   也就是说，重试本身可能是**制造**这个故障的帮凶之一。

边界（都是有意的，不是漏掉）：

- **标记只由 notion 路径挂上**（`tryNotionChannel` 的流内错误出口），所以其他渠道天然不生效——
  这就是"只接 notion、别家不接入"的落法。若哪天别家也学会说这句话，判据不用再改一次。
- **`notion-agent`（官方 Agent API）不挂这个标记**：它是另一条路径，自带 HTTP 状态码与 credits 语义
  （`workspace_credits_exhausted` 等），报文形状不同。
- **只跳过"同渠道重试"，不动「流断取回」兜底**（v1.18.39 的 `notionRefetchAnswer`）：后者是**另一套机制**，
  用同一 threadId 把 transcript 再发一次取权威全文，且它**真的救回过答复**。没有证据表明
  `isRetryable:false` 会让它必然落空，贸然关掉就是把一条已验证有效的兜底换成猜测。
- 标记是**调度内部**的（`[no-retry]`），`attemptErr` 在拼 502 的 `attempts` 前会剥掉它——
  客户端可见的报文里不出现内部记号，而失败原因照旧是那个可诊断的 `subType`。

回归：`test/per-channel-retry-e2e.test.js`（§8 跳过 / §9 对照组照旧重试 / §10 单候选 502 不带记号）。

## 候选游标：让**自动重试**前进（v1.18.62）

### 现场（三层时钟撞在一起）

| 时钟 | 值 |
| --- | --- |
| 客户端**单次尝试**（DSH） | 约 120s（超时后自动重试，最多 5 次） |
| 用户**整轮**（1 次 + 5 次重试） | 约 720s |
| 网关**一条候选链** | **没有总时长上限**：最多 13 家 × 每渠道死线（30~120s） |

而**首字超时的冷却只有 `COOLDOWN.transientBaseMs = 5000`（5 秒）**，重试间隔却是 **120 秒起步** —— 冷却早就过期了。于是：

- **每一次重试都从第 1 家重新开始**，5 次重试全砸在同一家上；
- 同时最多 **6 条链**在跑（1 条原始 + 5 次重试），每条都先碰第 1 家 —— **排在前面的坏家被反复吸住，排在后面的好家只有最老那条链能爬到**（第 8 家要 8×65s ≈ 520s 才轮到，那时所有人都走了）。

冷却的指数退避是 `5000 × 2^(连败-1)`：要涨到 160 秒（第 6 次连败）才追得上 120 秒的重试间隔，**而 DSH 只重试 5 次 —— 永远到不了第 6 次。**

### 处置

**① 客户端断开 → 立刻停链。** `res.on('close')` 置一个本请求的标志，候选循环**每次尝试之前**先查；已断开就带着真原因退出，不再试下一家。继续做的工必须有人等。

**② 候选游标。** 判据**不需要客户端配合**，只看报文：

| 报文 | 含义 | 起点 |
| --- | --- | --- |
| 与这一会话的**上一条逐字节相同** | 客户端**自动重试** | 上次真正试过的**那一家之后** |
| 变了（多了一条消息等） | 用户**新一轮** | **归零**，从第 1 家开始 |

过期（`ZZCSAPI_CHAIN_CURSOR_TTL_MS`，默认 15 分钟）也归零；成功路径直接 `return`，所以成功时不动游标（下一轮报文必然不同，自然归零）。

**只前移、不除名**：越过的家仍在链里，回绕之后照样会被试到。这是刻意的 —— 一个瞬时故障不该被粘成永久黑名单。

**★ 游标存的是「渠道 id」，不是「序号」。** **候选表不是稳定序列**：冷却中的家会被裁出去，同一个序号在下一发可能指向完全不同的家（第一版就是存序号，实测起点落在一个与上一发毫无关系的家上，整发一个上游都没碰到）。按 id 定位与顺序无关；那一家这轮不在候选里（被冷却裁掉）就**老老实实从第 1 家开始**。

> ⚠ 本仓最初把原因写成"候选表每一发都被加权轮询重排"——**那是错的**：一个 `weight` 都不填时 `pickWeighted` 的池子为空、完全空转，根本不会重排。真因是上面这条**列表进出**。

会话键取不到显式会话头时，退化成**前两条消息的哈希**（会话不可变的开头：系统提示 + 第一条消息）。**刻意不用 IP** —— 本机多窗口/多 agent 全是同一个 IP，按 IP 会把它们搅在一起。

**③ 每渠道死线上限 120s → 90s。** 由用户选定。硬约束：**必须小于客户端单次超时**，否则那一家永远得不到一次完整的尝试（客户端在它跑完之前就走了）。缩放仍在：`min(90000, 基础值 + 报文体KB × 40ms)`。

**④ 失败行记真实的规模与耗时。** `recordFailure` 此前写死 `inputTokens: 0, latencyMs: 0`，于是账本里失败行永远是 `in=0 out=0` —— "失败那发到底多大、在哪一家等了多久"完全看不见。现在用 `AsyncLocalStorage` 做**请求作用域**（`dispatchRequest` 包一层 `dispatchRequestInner`），`recordFailure` 自己取。**不能用模块级变量**：Node 虽单线程，但 await 会让并发请求互相覆盖，那会把 A 请求的耗时记到 B 请求的失败行上——比不记更坏。语义：**有作用域 = 真实流量写真实值；无作用域（探测/测试）= 0**。

## 熔断冷却（`cooldown`，按错误类型分级）

连续失败的渠道会被挪出候选链前段（`cooldownUntil`），时长按**同一渠道连续失败次数**指数增长。
关键是**按错误类型分开**——"网络抖一下"和"key 余额耗尽"需要完全不同的耐心，混用一条曲线是旧版的根本问题：

| 类型 | 什么算 | 起步 | 封顶 |
| --- | --- | --- | --- |
| `transient` 瞬时 | 超时、5xx、网络错误 | 5 秒 | 10 分钟 |
| `credential` 凭证/额度 | 401 / 402 / 403、key 失效、余额或额度耗尽、会话失效 | 5 分钟 | 6 小时 |
| `rate_limit` 限流 | 429（或上游报文里的限流信号） | 1 分钟 | 10 分钟；上游说了多久就照它等（`Retry-After` 头或**响应体里的 reset 时刻**，见下） |

- 曲线是 `起步 × 2^(n-1)`（第一次失败就是"起步"值），各自封顶。
- **两条欠账分开放（v1.18.40）**：`consecutiveFail` 只数**真实客户端流量**的连续失败；`probeFail` 数**探测与手动测试**
  （`/admin/api/recheck`、自动探测、控制台「测试模型」）的连续失败。冷却曲线读的是两者的**较大者**（`effFailStreak`），
  所以"只有探测在失败"照样会退避、照样能标记 `down`，但**测试/探测的成功绝不会动真实流量那条账**。
  两个字段都在 `/admin/api/status` 的每个渠道上返回。
- **连续失败 3 次** → 状态标记 `down`，排到候选链倒数第二（只在健康渠道都失败时才被撞）；
  冷却中的排最后。**探测成功只做"半愈合"**：冷却放开（有资格被再试）、`probeFail` 清零、状态变 `degraded`
  （排在健康渠道之后，且不进加权轮询的池子）——因为探测打的是 `/models`，它证明不了"对话能成"。
  **`consecutiveFail` 一字不动**（v1.18.40 起不再减半、更不清零）。要一次**真实对话**成功才会彻底清零、恢复 `ok`。
  唯一的例外是 workbuddy：它的探测本身就是一次真实对话，成功即真凭实据，直接满血。
- **为什么测试成功也不许清零真实流量的账（v1.18.40）**：熔断跳开死家**只**靠 `cooldownUntil`，而冷却时长按欠账指数增长。
  只要"点一次测试"就能把欠账清零，一个"测试过、真实挂"的渠道就会被反复拉回 **1× 退避**起步——
  现场表现就是"熔断永远跳不开这个死家"。手动测试是**可选、手动、且可能只覆盖一条路径**的，
  它不是"这家对话能用"的证据；所以它只还探测侧的账。测试失败同理只记 `probeFail`（不污染真实流量的账）。
- **测试要按真实姿势打（v1.18.40）**：控制台「测试模型」默认发**流式**请求（`stream:true`）——
  真实客户端走的就是流式，而上游完全可以"非流式答得好好的、流式那条路是坏的"。
  流式测试与真实链路**共用同一份帧分类**（`classifyStreamFrame`），所以"测试说好的"与"真实流量判好的"是同一把尺子。
- **★ 从响应体里读 reset 时刻（v1.18.95，思路抄自 magpie 的 `creditBackoff`）**：`Retry-After` 头只是上游
  **愿意说**的那一种；实测库里 429 **大多不带这个头**，却把"什么时候恢复"写在正文里。此前这些正文本就在手里
  （`recordFailure` 的 `msg` 就是 `HTTP 429: {…body…}`）却一个字都没用上，冷却只能按自己的曲线瞎猜。
  现在 `resetMsFromBody()` 覆盖三层，逐层尝试、解析不到就退回曲线（**绝不猜**）：

  | 来源 | 认哪些写法 | 例 |
  | --- | --- | --- |
  | 响应体 JSON 相对秒数 | `resets_in_seconds` / `resets_in_ms` / `retry_after` / `retry_after_ms` / `reset_after` | `{"resets_in_seconds":37}` |
  | 响应体 JSON 绝对时刻 | `resets_at` / `reset_at` / `reset_time` / `next_reset` / `renews_at` / `expires_at` | `{"resets_at":"2026-11-07T01:00:00Z"}` |
  | 自由文本时间戳 | `reset at 2026-09-28 10:00:39 UTC+8`（含 `Z` / `UTC` / `GMT` / `±HH:MM` / 无时区按 UTC） | WorkBuddy 原文 |
  | 自定义头 | `x-ratelimit-reset`（Unix 秒或毫秒，按大小判别） | — |

  **优先级链**：`Retry-After` 头 → 体/头里的 reset 时刻 → 自己的指数曲线。前两者都叫"上游明确说了多久"，
  收进同一个变量后**只在一处钳制**（`hardMaxMs`，6 小时）——所以坏上游没法用一个天文数字把我们钉住一天，
  而"冷却时长只有一个真源"这条装配守卫也照旧成立。

  **两条纪律**（都写在测试里）：① 解析出来是**过去**的时刻 = 上游报文陈旧，一律当成"没解析到"、退回曲线；
  ② 不含任何 reset 信息的失败（限流文案、积分不足、TLS 断连、超时、HTML 错误页）必须返回 `0`——
  **假阳性比不解析更糟**，那会让冷却时长乱跳。

  回归见 `test/upstream-reset-cooldown.test.js`（42 项，现抠 server.js 的真函数，含线上真实失败文案作为反例）。
- `Retry-After` 头只在**主路径**（OpenAI 兼容出站）读得到；curl 回退路径拿不到响应头。但**响应体**在所有路径都在
  `msg` 里，所以 v1.18.95 这一层对 curl 回退同样有效。
- **全部候选都在冷却时的 503 会说明原因**（v1.14.1）：不再只回一句 `all channels in cooldown`，
  而是附上每个候选的 `channelId`、`recoverIn`（还有多久恢复）与 `reason`（最后一条失败原文），
  例如「最近一家 workbuddy 约 2 小时 0 分后恢复：usage exceeds frequency limit …」。查"为什么今天用不了"时不用再翻日志。
- **被冷却跳过的候选也带原因**（v1.14.1）：混合场景（另一家真被试过、这家在冷却）走的是 502 那一支，
  其 `attempts[]` 里冷却项同样给出「还有多久 + 最后一条失败原文」与 `recoverInMs`，而不是一句光秃秃的
  `in cooldown`——因为"几小时额度恢复"和"刚抖了一下几秒后就好"是完全不同的处置。
- **观察期（`probation`）**：探测半愈合过的渠道会带这个标记——它排在健康渠道之后、
  不进加权轮询的池子、`/admin/api/status` 每个渠道都返回该字段（控制台/脚本可判读）。一次**真实对话**成功即清除。
- 调参（写在 `config.json`，缺省即上表）：

```jsonc
"cooldown": {
  "transientBaseMs": 5000,      // 瞬时故障起步（1s..300s）
  "transientMaxMs": 600000,     // 瞬时故障封顶（5s..24h），10 分钟
  "hardBaseMs": 300000,         // 凭证/额度类起步（10s..24h），5 分钟
  "hardMaxMs": 21600000,        // 凭证/额度类封顶（1min..7d），6 小时
  "rateLimitBaseMs": 60000      // 限流起步（1s..24h），1 分钟
}
```

> 改这些值前先想清楚：**起步调太短**等于拿真流量反复撞墙（每次请求都要先等它失败）；
> **封顶调太长**则"上游已经修好了"到"网关愿意再用它"之间的窗口会很大——凭证类封顶 6 小时就是为此留的折中。
> 探测的"半愈合"是这里的活路：改完 key 的渠道不用等满 6 小时，下一个探测周期就会回到兜底位。

## 加权轮询（`weight`，真正的按比例分流）

`priority` 与 `weight` 分工不同，别混：

| 字段 | 管什么 | 语义 |
| --- | --- | --- |
| `priority` / `effPriority` | **顺序** | 谁先试、谁兜底（排序语义） |
| `weight` | **分流** | 同一模型候选里按权重比例决定谁排第一（分流语义） |

- **只有明确填了正数 `weight` 的渠道参与轮询**；不填（缺省 `0`）时行为与从前**完全一致**，老配置零影响。
  `weight: 0` 与不填等价（只做兜底，不参与分流）。
- ⚠️ **上面这条只在自动权重关闭时成立**（v1.18.76 补：原文没写这个前提，用户照它理解会以为"开了自动权重还得手填 1"）。
  打开 `autoWeight.enabled` 后生效权重是 `(手工 weight ‖ 1) × h`，基底取 `1` 正是为了让"一个 `weight` 都不填"的家
  **全部进池**；所以那时 **`weight: 0` / 留空 / 填 `1` 三者完全等价、都会进池**，`weight: 0` **不再等于"排除"**。
  要真把一家排除出候选，只有**停用渠道**（`enabled: false`）一条路。公式与四条护栏见下面「自动权重」一节。
- 参与轮询的渠道来自**同一 (模型, 协议) 的候选集**，按权重比例分流：两个渠道 `3:1` ⇒ 长期 ≈ 75% / 25%。
- 算法是**平滑加权轮询**（nginx upstream 同款 smooth WRR，无随机数）：长期比例精确等于权重比，
  且**不会突发扎堆**（纯加权随机会连着命中同一个渠道）。
- 轮询只决定**谁是第一位**；其余候选保持原有「健康度 → 有效优先级 → 延迟」顺序作**兜底链**
  （如果轮到的那家正好挂了，下一个还是按老规矩顶上来）。图片生成候选（`/v1/images/generations`）同一套规则。
- 冷却中 / `status=down` / `probation`（探测半愈合过的观察期）/ `weight=0`（**仅自动权重关闭时**——开启后 `weight: 0` 也会进池，见上一条）的渠道**不进池**，其份额自动分给健康成员；
  它恢复后也不会"补发欠账"（不出现报复性突发）。
- **与会话粘性的关系（v1.17）**：粘性命中时，轮询选出的"第一位"会被粘住的那家顶掉，但**轮询状态照旧推进**——
  所以份额统计（`weightedShare`）反映的是"轮询怎么分的"，不是"流量实际落哪"，两个数字**故意不同**
  （落点 100% 在一家、份额仍 50/50 是正常现象；`test/session-affinity-e2e.test.js` 有专门断言）。
- 状态是内存态（重启清零，无副作用）。改权重三种方式，效果一样：
  · **控制台**：渠道页 → 该渠道「编辑」→ 表单里的「权重」框（**关闭自动权重时**留空 = 0 = 不参与；
  开启后留空 = 基底 1 = 照样进池，见上一条），保存即生效并持久化；
  · 直接改 `config.json` 的 `"weight": 3` 后重启；
  · `POST /admin/api/channel` 带 `{id, weight}` ⇒ **立即生效并持久化，无需重启**。
- 可观测：`/admin/api/status` 每个渠道返回 `weight`（配置值）、`weightedHits`（**真实派发里被轮询选中**的次数）、
  `weightedShare`（占全部命中的百分比）；控制台**渠道表格有「权重 / 分流」列**（`3 · 24%`，
  悬停看命中次数），**渠道详情抽屉**顶部另有角标。没配权重的渠道显示 `—` 而不是 `0%`
  ——`0%` 会被误读成"配了但一次都没分到"。
- ★ **一次请求只记一次命中，而且只记"真正竞争的那个池"（v1.18.76 修）**：一次客户端请求会把各协议
  候选拼成一条链（openai 客户端下要逐个查 9 个协议族），但**只有第一个有候选的池**才是这次请求真正
  竞争的池，排在它后面的全是兜底层（只有前面的层全挂才走得到）。三条纪律：
  ① **「选中」与「记账」是两步**——`applyWeightedPick` 只在赢家身上打标（`weightedPicked`），
  `countWeightedHit` 才记一笔；② 三条客户端链（openai / anthropic / gemini）组装完后**各记一次**；
  ③ **纯枚举不推进任何状态**——管理面「手动测试」以及一切"只想看有哪些候选"的调用走
  `channelsServing(model, proto, { pure: true })`：不推 SWRR 相位、不选链首、不记账。
  **为什么必须这么改**：此前命中记在 `pickWeighted` 里，而它被纯枚举调用了 8 次，于是**只有一条渠道的
  兜底协议（workbuddy / opencode）每个请求白得 1 次命中**——控制台那列份额恒为 ~1/3，而它**一次都没被
  派发过**（实测 33.7% / 30.1% 就是这么攒出来的：每个请求 openai 池 1 次 + 两个兜底池各 1 次，
  三家恰好各占 1/3）。回归：`weighted-rr-e2e` 第 5 节（兜底渠道恒 0 + 合计命中 = 请求数 +
  管理面手动测试不动统计）与 `weighted-rr.test.js` 第 8/9 节（打标 / 记账 / pure 三条结构性守卫）。
- 权重接受任意非负数字（整数最好懂：`3:1` 就是 75/25；小数同样按比例算）。负数、非数字在控制台表单里
  就被挡下（不会发请求），绕过前端直接调接口也会被后端拒（400）——两边校验规则一致。

## 自动权重（v1.18.63 起可选用：观测永远算，`enabled` 决定用不用）

> **v1.18.63 起这一段不再是"无条件只算不生效"**：`autoWeight.enabled: true` 现在表示**真的生效** ——
> 把观测算出的健康系数 `h` 乘进候选的权重（`effWeight`），从而真的影响"谁排第一"。
> **关闭时逐字节回旧行为**：`effWeight` 原样返回 `ch.def.weight`（没填就是 0）→ `pickWeighted` 的池子为空 →
> 返回 −1 → `applyWeightedPick` 什么都不做。旧配置零影响靠的就是这条**空转路径**，不是"结果看起来一样"。
>
> 三条边界，破坏任一条都是真 bug：① **观测与生效解耦**——观测节拍**永远建**（关了生效也看得见"如果开着会怎么分"，
> 那份预测正是判断该不该开它的依据）；② **`enabled` 是运行期可改的**（`POST /admin/api/settings` 第五组 +
> `persistConfig` 白名单已有 `autoWeight`，否则一次渠道保存就把开关抹掉）；③ **只前移不除名**——
> `h` 有地板 `floor`，失败家份额掉到地板、一旦成功立刻回升，**没有任何永久状态**。
>
> 公式：`有效权重 = (手工 weight ‖ 1) × h`。手工权重是**意图**、h 是**现实**，相乘语义最自然；
> 基底取 1 让"一个 weight 都不填"的家也全部进池（这才是"不配置也能自动分流"的关键）。
> 护栏仍是原有的四道：`ewma` 平滑、`deadband` 死区、`minSamples`（新家不被噪声打死）、`updateMs`（不跳变）。
> 回归：`test/auto-weight-apply-e2e.test.js`（开启态：不健康那家真被碰到过、且明显少）+
> `test/auto-weight-e2e.test.js`（关闭态：分流逐字节不变、加权命中恒为 0）。

想让"同一个模型有很多渠道都提供、有的能用有的不能用、有的快有的慢"这件事**自动**按实测表现分流，
不用手填 `weight`。v1.6 最初只上**观测版**（只展示、不生效）；**v1.18.63 起 `enabled` 才是真正的开关** ——
打开就按上面的公式把 `h` 乘进权重、**真的改分流**；关掉就逐字节回旧行为。控制台那张卡一直看得见
"若开着会怎么分"，那份预测正是判断该不该开它的依据。

> **历史上为什么推迟**：自动权重天然有反馈回路（份额改流量 → 流量改统计 → 统计改份额），
> 先让人对着真机数据确认它算得对、再打开开关，是成本最低的顺序。这个理由如今仍然成立，
> 所以四条护栏（`ewma` / `deadband` / `minSamples` / `updateMs`）不是装饰。

**怎么打开**：两条路都行 —— ① 控制台「运行期设置 → 自动权重」拨开关，**即时生效、即时落库**（推荐）；
② `config.json` 顶层加 `"autoWeight": { "enabled": true }` 后重启。
⚠️ **开关与旋钮的时间尺度不同**：`enabled` 是**运行期即时**的；而 `updateMs` 等旋钮只在启动时读一次
（节拍周期 = 启动那一刻的 `updateMs`），改旋钮要重启 / 重建容器。打开后后端**按 `updateMs` 自己走节拍**（见下），
不需要你开着控制台。

> **观测数据的时间尺度（重要，别按字面理解成"一个月统计"）**：
> 健康系数只有两个来源，都是**近期窗口**、都**只存在内存里**：
> - 成功率来自 `ch.roll` —— 与「有效优先级」同一个滚动窗口，累计到 120 次后**整体减半**（旧样本指数衰减）。
>   所以它回答的是"**这家最近几十到一百次请求稳不稳**"，不是长期累计；**容器重启清零**。
> - 速度来自成功请求延迟的 EWMA（α=0.3），同样是内存态，重启清零。
>
> 换句话说：跑几天之后你看到的，仍然是"**最近**的表现"。这恰恰是它要用的信号（预告的是"如果现在生效会怎么分"），
> 但它**不会**替你记住一周前的长期稳定性；那需要 `usage.json` 的 `byChannel` 那类落盘统计，未来才可能接。

**开着它之前 / 之后，判断"算得对不对"要看什么**：

1. `candidates[].h` 是否会**稳定下来**（不是每小时换一个样）——OLAP 抖得厉害说明死区还不够；
2. 预测份额和你**心里的预期**是否一致（哪家该多、哪家该少），特别是"慢但质量好"的那几家有没有被过度压制；
3. `samples` 够不够：低于 `minSamples`（默认 10）的渠道**只有速度项在起作用**，失败率还没资格发言——
   长尾模型上多数渠道都可能一直没样本，那些模型就别指望自动分流。
4. **从没被用过的渠道在预测里天然占便宜**：没有延迟数据 = 不因速度扣分，样本为 0 = 失败率按满分算，
   于是它的 `h` 就是 1，看起来"完美"。这不是 bug（观测无法区分"没试过"和"从没出错"），但它意味着
   **一旦生效，这些从未承载过流量的渠道会立刻开始分到份额**——它们真正的成色要等生效后头几笔请求才看得出来
   （表现差会被失败率与冷却接手）。反过来说，这也是"自动发现更好的渠道"的那一半价值。

**健康系数 `h`（0.2 ~ 1）** 由两个**已有**信号合成，不引入新统计：

| 信号 | 来源 | 作用 |
| --- | --- | --- |
| 成功率 | 滚动窗口 `ch.roll`（与「有效优先级」同一个窗口） | **主力**：`h = 1 − 失败率` |
| 速度 | 该渠道最近成功请求的延迟指数平均（EWMA） | **温和**惩罚：慢 2 倍只打到 `0.75`（默认 `latencyPenalty: 0.5`） |

**抗振荡三件套**（自动调权最怕的就是抖）：低频重算（`updateMs` 默认 30 秒）+ 指数平滑（`ewma` 0.5）+
死区（变化小于 `deadband` 10% 就不动）。另有四条护栏：

- **失败率样本不足不动**（`minSamples` 默认 10 条）：新渠道不被几次随机失败打死；
  注意**只管失败率这一项**——样本不足时该项按"满分 1"算，但**速度项仍独立生效**
  （所以一个刚上线、样本为 0 但延迟很慢的渠道，`h` 仍可能 < 1；这是刻意的，实测延迟不需要攒样本就够可信）；
- **地板**（`floor` 默认 0.2）：慢/差也不给 0——"慢"常常是长上下文模型在思考，饿死它反而丢质量；
- **单渠道上限**（`maxShare` 默认 70%）：防赢家通吃（最快的被打爆后反而更慢）。
  上限**只兜自动算出来的份额**；用户手填的 `weight` 永不封顶（手填是硬意图，护栏不该反过来压制它）；
- **冷却 / `down` 的渠道直接排除**（本来就进不了池），其份额分给健康成员。

配置项（`config.json` 顶层，全部可选，`config.example.json` 里有全量示例）：

| 键 | 默认 | 含义 |
| --- | --- | --- |
| `enabled` | `false` | **生效开关**（运行期可改）：`true` = 健康系数乘进候选权重、**真的影响分流**；`false` = 一行不碰。观测与它**解耦**，两种状态下都跑 |
| `minSamples` | `10` | 滚动窗口样本少于它就**不按失败率扣分**（速度项不受此门槛约束） |
| `floor` | `0.2` | 健康系数地板 |
| `latencyPenalty` | `0.5` | 速度惩罚强度；`0` = 完全不看速度 |
| `maxShare` | `70` | 自动份额的单渠道上限（%）；手填权重不受限 |
| `updateMs` | `30000` | 健康系数重算间隔（毫秒，最小 1000）；**同时是后台节拍的周期** |
| `ewma` | `0.5` | 新值权重（指数平滑） |
| `deadband` | `0.1` | 死区（相对变化小于它就不动） |

**后台节拍**：健康系数是"一拍一算"的（指数平滑 + 死区），而它最初的触发点只有 `/admin/api/status`
——等于**没人开着控制台就没有观测数据**，`h` 会永远停在上次打开控制台那一刻的值。
**v1.18.63 起这个定时器无条件建**（不再由 `enabled` 决定）—— 关了生效也要看得见"如果开着会怎么分"。
它跑的是同一个**只读**观测函数（不碰 `SWRR_*`、不改 `ch.def`、不发请求），**改不改分流只由 `effWeight` 那一层决定**；
`/admin/api/status` 的 `autoWeight.ticks` 是**只数后台定时器那一路**的拍数，
用来从外部证明节拍真的在跑（控制台拉 status 那一路不计入，否则这个数字就说明不了问题）。

可观测与界面：

- `/admin/api/status` 新增顶层 `autoWeight`：`enabled` / **`effective`（= `enabled`；为 `false` 时一眼看出没生效）** /
  `knobs` / `at` / **`ticks`（后台节拍拍数）** / `models[]`。每个 `models` 条目 = 一个"被多个渠道提供的模型"：
  `candidates[]` 里给出预测份额 `share`、健康系数 `h`、基础权重 `base`、是否手填 `manual`、
  当前手工份额对照 `nowShare`、以及**判断依据**（`failRate` / `samples` / `latMs` / `speedRatio`）；
  `excluded[]` 是冷却或 down 而没参与分份额的候选；`manualOff` 表示当前压根没开加权轮询。
- 每个渠道新增 `autoH` / `autoFailRate` / `autoSamples` / `autoLatMs` / `autoSpeedRatio`。
- **控制台**：**「资源 → 自动权重」独立页**（v1.9 起从渠道页迁出）有份额预测卡，按模型列出预测份额
  （每个候选一列，列宽即份额，色带段下方直接挂渠道名与百分比；含"当前 x%"对照与被打折的原因）；
  渠道详情抽屉里有「自动权重（观测）」一节，把健康系数、样本数、失败率、延迟摊开——**这些正是 `h` 的输入，生效时就是份额的依据**。
  单候选模型不进卡（一个提供方谈不上分流，显示了只会是"100%"噪音）。

## 有效优先级（失败率自动降权）

同状态渠道不是死板按配置的 `priority` 排，而是按**有效优先级** `effPriority`：

```
effPriority = priority − 失败率 × 3
```

- 失败率取自**滚动窗口**（`ch.roll = {w,f}`，成功/失败各累加一次，样本 ≥ 5 才开始生效，累计 120 次后减半衰减）
- 也就是说：一个配置 `priority=10` 但近期失败率 40% 的渠道，有效优先级降为 `8.8`，会被配置 `priority=9` 的健康渠道反超
- 失败率回升时被新成功样本稀释，优先级**自动恢复**，不需要人工干预；配置值本身不被改写
- 失败计入点：主调度失败、探测失败都走 `recordUsage` → `bumpRoll`
- 控制台「渠道管理」在渠道被降权时显示 `→ 有效 X（失败率 Y%）` 角标（数据来自 `/admin/api/status` 的 `effectivePriority` / `rollFailRate` 字段）

## 含图请求的候选裁剪（图片能力门）

请求体里带图片时（内部统一格式 = OpenAI，即 `messages[].content` 数组里的 `image_url` block），候选链**只保留能原样/等价转发图片的渠道**：

```
IMAGE_CAPABLE_PROTOCOLS = ['openai', 'anthropic', 'gemini', 'workbuddy']      # server.js
```

- 四种协议各自的带图出站方式：`openai` 原样转发 `image_url`；**`workbuddy` 同为 OpenAI 兼容面、也原样转发 `image_url`**（v1.18.82 实测：1×1 PNG 直传上游 → HTTP 200 且模型答出了颜色，即"图真的到了模型"）；`anthropic` 转成 `image` 块（`source.type = base64 | url`）；`gemini` 转成 `inlineData`（data URL）或 `fileData`（http 链接）。
- **为什么必须裁剪**：`notion` / `notion-agent` / `hark` / `genspark` / `codex` 这几条**文本仿真/网页会话**链只把 `content` 当字符串用；`opencode` 则把 `messages` **拍平成单个 prompt 字符串**，图无处可放。把带图请求丢过去，图会被**静默丢掉、模型照样自信作答**——用户以为它看过图。这比直接失败更糟，所以宁可明确报错。
- **判据是"图能不能真送到模型"，不是协议名好不好看**：`workbuddy` 的协议名不叫 `openai`，但它走的是原生 `{...body}` 透传（见 [docs/protocols.md](protocols.md)「workbuddy」一节），所以它在名单里；反过来，一个"名字像 openai 但内部拍平文本"的渠道绝不能因为名字而混进来。
- **裁干净了怎么办**：返回 400 + `this request contains images, but no channel can forward them: only <名单> protocol channels can carry images`——**这段文案里的名单由 `IMAGE_CAPABLE_PROTOCOLS.join(' / ')` 拼出，不许再手写一份**（手写的那份在加 workbuddy 时已经过期过一次：文案说"只有三家"、名单已经四家，正是文档/文案漂移的典型）。不是 404、不是降级重试、不是静默丢图。
- **纯文本零影响**：`bodyHasImages()` 为假时函数原样返回同一个候选数组，排序与老行为逐字节一致。
- 三条客户端协议共用这道门：`/v1/chat/completions`、`/anthropic/v1/messages`、`/gemini/v1beta/...`（Anthropic 的 `image` block 与 Gemini 的 `inlineData`/`fileData` 都先转成内部 `image_url`，因此判定点统一；`/v1/responses` 亦接同一道门，共 4 处调用）。
- 回归：`node test/gemini-multimodal.test.js`（含"含图 → 只留可转图渠道（openai + workbuddy）/ 纯文本 → 候选链原样 / notion·opencode 仍被挡"三组断言 + 400 文案由常量拼出的守卫）+ `node test/native-channels-e2e.test.js`（原生化后仍带图）。
