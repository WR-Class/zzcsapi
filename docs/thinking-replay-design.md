# thinking 回放缓存 · 设计稿（v1.18 候选，**已验证：现有实现下无收益，暂不实现**）

> 状态：**只有设计，没有代码**。这份文档记录了一次"先验证再动手"的过程：
> 提出特性 → 逐行核对现状 → 发现**最初的假设是错的** → 用测试把事实钉死 → 得出"不做"的结论。
> 事实的可执行版本在 [`../test/thinking-fidelity.test.js`](../test/thinking-fidelity.test.js)（36 项断言）。
> 相关实现：`server.js` 的协议转换层、v1.15 同协议直通、v1.17 会话粘性。

---

## 1. 问题到底是什么

### 1.1 背景

Anthropic 的思维链（`thinking` 块）带 **`signature` 签名**，官方要求：**多轮工具调用时，
上一轮的 `thinking` 块必须原样回传**（含签名）。本网关的内部统一格式是 **OpenAI**，
而 OpenAI 格式**没有**承载签名的地方 —— 看起来这里必然有损失。

### 1.2 ⚠️ 最初假设 vs 实测事实（这是本设计稿最重要的部分）

初稿断言：「Anthropic 客户端 → OpenAI 渠道时，上游的 `reasoning_content` 会被映射成 `thinking`
块回给客户端，**但没有签名** → 客户端再把这个无签名块带回来 → 上游校验失败 400」。

**这个假设是错的。** 逐行核对 `server.js` 后的事实（每一项都有断言守着）：

| 链路 | 实测行为 | 出处 |
| --- | --- | --- |
| Anthropic 客户端请求 → 内部 OpenAI 格式 | `thinking` / `redacted_thinking` **整块丢弃**（刻意；OpenAI 上游没有签名校验需求，回塞 content 反而污染上下文） | `anthropicToOpenAI`（1475） |
| 原生 Anthropic 上游响应 → 内部 | thinking 的**文本**进 `reasoning_content`，**签名丢掉** | `anthropicToOaiResponse`（2063–2078） |
| 原生 Anthropic 上游**流式** → 内部 | `thinking_delta` → `reasoning_content` 分片，**签名丢掉** | `createAnthropicToOaiStream`（2135） |
| 内部 → **Anthropic 客户端**（非流式） | **不产出** `thinking` 块（只有 text / tool_use） | `openAIToAnthropicResponse`（1587） |
| 内部 → **Anthropic 客户端**（流式） | **不产出** `thinking` 块 | `createAnthropicStreamConverter`（1637） |
| 内部 → **原生 Anthropic 渠道**（出站） | **不产出** `thinking` 块（即使消息上挂着 `reasoning_content`） | `oaiRequestToAnthropic`（1956） |
| Anthropic 客户端 → Anthropic 渠道（同协议） | **逐字节直通**：thinking 与**签名都原样活着** | v1.15 `passthroughChannelOpts` |
| 全仓 `signature` 出现次数 | **0 次**：网关既不保存、不校验、也不伪造签名 | `grep -c signature server.js` |

### 1.3 结论：可达的失败模式只有一条，且**回放缓存治不了**

1. 「客户端回传**无签名的** thinking 块 → 上游 400」——**不可达**：客户端从我们这里**根本收不到**
   thinking 块（只有同协议直通会给，而那条路给的是**带**签名的原件）。
2. 真正会 400 的场景是：**客户端自带的、属于渠道 A 的签名，被发到了渠道 B**（切换/故障转移后）。
   但这条**恰恰是回放缓存解决不了的**——缓存里存的也是渠道 A 的签名，一样过不了渠道 B 的校验；
   而且网关在这里的行为是**正确的**（原样转发客户端的块，不篡改）。
3. 真实存在的损失只有一种：**跨协议时思维链内容被丢弃**（Anthropic 客户端 ↔ OpenAI 渠道）。
   这是**刻意的设计**（`server.js` 有注释说明），且回放**签名**对它毫无帮助——
   OpenAI 协议侧上游（DeepSeek 一类）明确要求不要回传 `reasoning_content`。

**所以：在现有实现下，做一张按会话驻留的 thinking 回放表，解决不了任何可达的问题。**
它只会增加内存、增加一处"往用户请求里回注历史内容"的风险面（注错了不报错，只让推理悄悄变味）。

### 1.4 什么情况下才值得重新考虑

必须先改变下面任一项（都属于"改协议转换层的产出"，而不是加缓存）：

- 让「内部 → Anthropic 客户端」开始产出 `thinking` 块（则必须同时解决签名从哪来——只能来自直通，
  即必须**同一会话同一渠道**，这就变成 v1.17 会话粘性的子问题，而不是缓存问题）；
- 或者支持某家**真的接受无签名 thinking** 的上游（此时连缓存都不需要，直接转发即可）。

在此之前，本特性**标记为"已验证无收益"**，不排期。

## 2. 目标 / 非目标（**保留备查**：若 §1.4 的两个前提之一被满足，才回到这一节）

**目标**
- Anthropic 客户端在**跨协议**链路上的多轮工具回合中，能把上一轮的 thinking 块**带签名**回传；
- 命中不到就照旧丢弃（宁可少一个字段，不许编造）。

**非目标**
- ❌ 不跨会话共享、不跨渠道共享（签名与账号绑定，跨渠道回放只会制造 400）；
- ❌ 不生成/伪造签名，不做"签名猜测"；
- ❌ 不改变同协议直通路径（那是逐字节路径，一个字节都不许动）；
- ❌ 不做跨格式的思维链**改写**（只做原样存取）；
- ❌ **（v1.18 前新增）不为了"能缓存"而开始向客户端产出无签名的 thinking 块**——那是把风险从"丢内容"
  换成"制造上游 400"，方向完全错了。

## 3. 键设计

复用 v1.17 已经落地的会话键（`affinityKeyFor`），再叠加**渠道**维度：

```
replayKey = sessionKey + '|' + channelId + '|' + model
```

- `sessionKey`：与粘性同一套推导（显式头 → 正文标识 → 可选正文哈希）。**取不到会话键就不回放**——
  没有会话边界就没有安全边界，"随便找一条最近的思维链塞进去"比丢弃更糟。
- `channelId` 必须在键里：签名与上游账号绑定（§1.2 ③），这也是与同类项目最大的行为差异——
  它们默认"同一凭据池内可回放"，我们**只承认同一渠道**。
- `model` 在键里：换模型后的思维链语义不同，不互相污染。

## 4. 存什么

每条记录（内存 Map，进程内，重启即失）：

| 字段 | 来源 | 说明 |
| --- | --- | --- |
| `thinking` | 上游响应 / 入站请求的 thinking 块 | 原文，不做任何改写 |
| `signature` | 同上 | **没有签名的记录不存**（存了也没用，见 §2） |
| `redacted` | `redacted_thinking` | 与 `thinking` 分开存，回放时按原类型回 |
| `budget` | 请求里的 `thinking.budget_tokens` | 只用于观测，不参与回放决策 |
| `ts` / `turn` | 本地 | 过期判断与"只回放最近一轮" |

- 上限：`maxEntries`（默认 **2048**）+ `ttlMs`（默认 **1 小时**）。淘汰策略：超限时丢最旧（Map 插入序）。
- 参考量级：CLIProxyAPI 用 LRU 10240 条 / TTL 1h。我们默认更小——单机自用，宁可少占内存。

## 5. 回放时机（唯一的注入点）

只有一个注入点，且必须是"缺什么补什么"：

- 在 **Anthropic → OpenAI 请求转换**里，当遇到 `assistant` 消息带有 `tool_use` 块、
  且该消息**没有** thinking 块时：按 `replayKey` 查表，命中则把存下的 thinking 块（含签名）**加回转换结果**。
  未命中 → 维持现状（丢弃），并把 `miss` 计入观测。
- 在 **OpenAI → Anthropic 响应转换**里：把上游的 `reasoning_content` 映射成 `thinking` 块时，
  **顺手把这一轮的 thinking 写入表**（这是唯一的学习点）。
- **不做的事**：不主动往请求里插新 thinking 块；不在直通路径上查表；不在流式响应中间插帧。

## 6. 观测与护栏

- `/admin/api/status` 暴露 `thinkingReplay: { enabled, entries, hits, misses, evicted, expired }`；
  `/metrics` 暴露 `zzcsapi_thinking_replay_events_total{event}` 与 `zzcsapi_thinking_replay_entries`。
- 护栏：
  - 默认**关闭**（与 v1.17 三个开关同一风格）；
  - 命中率若长期为 0，说明适配的场景不存在——文档里应有人据此决定**退役**这个特性（而不是留着当摆设）；
  - 上游因签名问题返回 4xx 时，把这条记录**立即删除**（避免同一条坏记录反复引发 4xx），并计入 `stale` 计数。

## 7. 验收标准

### 7.1 第 0 步（**已执行：结论是"不要实现"**）

初稿写的第 1 条是「先证明问题存在，没复现出来就不要实现」。这一步真的做了，做法与结果：

- **做法**：不靠印象，直接把 `server.js` 的转换层函数**按花括号配对抠出来**在沙箱里跑，
  拿带 `signature` 的 thinking 块过一遍每一条链路，并把结论固化成
  [`../test/thinking-fidelity.test.js`](../test/thinking-fidelity.test.js)（36 项断言，含 9 条源码级装配守卫）。
- **结果**：见 §1.2 的事实表 —— 「客户端回传**无签名** thinking → 上游 400」**不可达**；
  唯一会 400 的场景（签名跨渠道）**回放缓存也治不了**。
- **决策**：**不实现**。本文件保留作为"为什么不做"的记录；将来若 §1.4 的前提改变，再回到下面的清单。

### 7.2 若将来重启本特性，必须满足

1. 先复现一个**真实的**失败：跨协议多轮工具回合里，客户端确实收到了我们产出的 thinking 块、
   并确实因为签名问题被上游拒（假上游做签名校验，记录它收到的原始块）。**复现不出来就不写代码。**
2. 开启后：同会话同渠道的相邻轮次，上游**真的收到**带签名的 thinking 块（逐字段比对）；
3. 不同会话 / 不同渠道 / 不同模型 → **绝不回放**（三组反向断言）；
4. 过期 / 超限淘汰后不回放，且计数正确；
5. 直通路径（Anthropic 客户端 → Anthropic 渠道）**字节级不受影响**（复用 `same-protocol-passthrough` 的断言）；
6. 上游 400 时记录被删除，第二次不再回放同一条（`stale` 计数 +1）；
7. **本文件的 §1.2 事实表与 `thinking-fidelity.test.js` 必须同步改写**——保真度地图变了，
   不能让那份地图和实现各说各话。

## 8. 风险（**仅在该特性真的被实现时才需要读**）

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 误回放（会话键识别错、把别人的思维链塞进去） | 语义污染，且**很难发现** | 只在显式会话键命中时回放；取不到键不回放；不同渠道绝不跨 |
| 签名过期/失效 | 上游 400 | 收到签名类 4xx 即删记录；`stale` 计数可观测 |
| 内存占用 | 长跑进程膨胀 | 默认 2048 条上限 + 1h TTL；条目只存文本，不存整个响应 |
| 与 `cache_control` 相互作用 | 前缀变化导致缓存失效 | 回放只加在 `assistant` 的 thinking 块上（不在前缀区），并在测试里断言不改前面的消息 |
| 复杂度 | 多一张驻留表、多两处接线 | 关闭时零行为；观测三段齐全，便于判断它是否值得留 |

## 9. 决策记录（两次收紧）

- **v1.17 时**：它是**唯一一项需要"往用户请求里回注历史内容"**的改动——注错了不会报错，只会让模型推理
  悄悄变味，失败模式与"限流/粘性/指标"完全不同量级，所以先只落设计稿。
- **v1.18 前置验证后（最终）**：按 §7.1 的要求真的去复现问题，结果**问题在现有实现下不可达**（§1.2/§1.3），
  而唯一可达的 400 场景（签名跨渠道）回放缓存也治不了。**结论：不实现**，
  并把现状固化成 [`../test/thinking-fidelity.test.js`](../test/thinking-fidelity.test.js)。
- **这条路径本身的价值**：一个被写进路线图、看起来"必须做"的特性，用一天不到的核对就被证伪了——
  代价是 36 条断言和一份文档，而不是一张驻留表、一处回注逻辑和一堆难以复现的"推理变味"工单。
